Scoped Search — search UI with collection scope selector

The Problem

Open access with granular filter creates an overwhelming experience

Content in Highspot is organized into folder-like constructs (spots), each with its own access control. When items are added, the owner make a decision about the spot it belong to.

When reps search, they think in terms of broad content areas (a product line, a vertical, or a sub-org). The platform search does not map to those boundaries. Reps can filter results by spot, but spots are too granular to represent a product area or a vertical, and selecting the right combination of spots requires organizational knowledge that most reps do not have.

Content Collections as promoted filters in the search results page

A NEW FILTERING CONSTRUCT

Content Collections make searching within a broad area possible

To make scoped search possible, we first introduced content collections — an admin-defined grouping of related spots. Once a collection is configured, item-to-collection association becomes automatic.

Collections can map naturally to how large orgs already think: by sub-org, product line, or region. This becomes a useful contrsuct for reps to limit their search results to a broader area. .

Early exploration — two interaction models

The Design Challenge

How might we limit search results to a content collection?

The initial exploration examined two interaction models for limiting search results to a content area.

01

Scope before the query — in the search dropdown

The user selects a content collection before typing. The scoping interaction happens in the dropdown. The assumption at this stage was that any available collection could be a valid scope — and the platform supports up to 50 collections, which meant the dropdown needed to accommodate a potentially large selection set.

02

Filter after the query — on the search results page

The user submits a query first, then filters results by collection. This is standard filter behavior: a collection appears as a filter option only if at least one result in the result set belongs to it. The available filter options are determined by what the search returns, not by what the user intended to search within.

The Research Finding

Most sales reps will frequently engage with 1–3 collections

The team returned to customers with a focused question: how many collections do users actually have access to, and how many do they use when searching?

The data showed that users with access to many collections consistently engaged with only 1–3. This finding established the core design principle for the interaction: make frequent tasks easy, and less frequent tasks possible.

Promote scoping to frequent collections — in the dropdown
The 1–3 collections most relevant to the user are surfaced directly in the search dropdown, allowing the user to scope before submitting. Fast, contextual, low friction.
Allow filtering to other collections post-search
For less frequent cross-collection searches, the sidebar filter handles it — exactly like any other facet. The dropdown stays clean. The sidebar scales to edge cases.

Design Principles

Identify and design every state

Each keystroke, each pause, and each click changes the state of the dropdown. Each of those states needs to be identified and designed explicitly.

Transition states need to be designed so that the perceived speed of the interaction exceeds the actual response time, and so that the state changes occurring with every keystroke feel seamless to the user.

01
Optimize for simplicity
Scoping should require a single quick action. Each additional decision point in the dropdown increases the effort required to complete a search.
02
Fluid transition between states
Transitions need to be smooth enough that the user perceives the surface as continuously responsive, and designed so that perceived speed exceeds actual response time.
03
Dropdown is prime real estate
The search dropdown is reserved for the most frequent actions. Less common filtering needs are handled by the sidebar filter panel on the results page.
The State Model

Schematic breakdown of a search interaction.

Even though the search interaction takes place in a matter of seconds, the search dropdown goes through multiple states. Breaking the interaction down into distinct states helps identify the most relevant information to surface to the user at each point. Stitching those states together with well-designed transitions makes the interaction feel relevant and smooth throughout.

01

Rest - No interaction has happened yet.

The search bar is visible and discoverable. The design goal is to make search easy to find and invite interaction without introducing distraction.

02

Zero state - The user has clicked in.

Intent is unknown. The dropdown surfaces recent searches to give the user a fast path back to queries they have already run.

03

Auto-suggest - The user is actively typing.

The dropdown surfaces keyword and entity suggestions that update with every keystroke. Transitions need to be smooth enough that the surface feels continuously responsive.

04

End state - The user has submitted a query.

Search results are displayed in this state. The design provides clear affordances for adjusting the query, changing the scope, or starting a new search with minimal steps.
