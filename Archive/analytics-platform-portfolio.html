Designing coherence for the analytics platform

When I joined the analytics team, the experience was a collection of components without platform-level guidance. Individual scorecards had been built independently, each with its own structure, chart conventions, and interaction patterns. I worked across three layers to bring coherence to the platform: modernizing the component foundation, improving quality-of-life interactions, and proposing a system-level information architecture for scorecards.

Starting State

Design was contributing components, not direction

The working model before I joined was a two-SME collaboration: a Product Area SME who understood the customer questions being asked, paired with an Analytics SME who knew the platform capabilities and data availability. Design contributed by supplying components, but did not own large-scale guidance, information architecture, or experience consistency across scorecards.

The result was a set of scorecards where each one had been designed somewhat independently. Chart conventions, tooltip behavior, empty states, and tab structures varied across item types. Customers had to re-learn the experience every time they encountered a new scorecard.

The Approach

Three layers of work, ordered by altitude

I structured my contribution across three layers, each building on the one below it. The first layer addressed the component foundation. The second layer improved interaction patterns that affected every scorecard. The third layer proposed a system-level structure for how scorecards should be organized.

Layer 1
Component Modernization

Extending component work to include guidance, not just building blocks

The existing component library needed updates to meet accessibility standards and align with the broader design system. I completed that work, but components alone were not preventing inconsistency. Different designers and PMs were making different charting decisions for the same kinds of data.

I introduced a tiered data visualization guidance system on top of the components. The tiers were ordered deliberately so that anyone building a new scorecard would exhaust existing patterns before creating a new chart.

Data Visualization Guidance

Three tiers, ordered to prevent unnecessary variation

The ordering was the design decision. By prioritizing scenario-based guidance first, the system directed people toward reuse before they reached the tier where new chart decisions were needed.

Tier 1

Scenario-based

For data about items that already exist in Highspot, the chart type, color mapping, and segment order were fully specified. For example, course completion status used the same colors and segment order in every scorecard. These charts were used as-is with no design decisions required.

Tier 2

Analysis-type

For common analytical patterns, the visual treatment was standardized by analysis type rather than by data domain. Trend charts looked the same everywhere. Distribution charts looked the same everywhere. Comparison charts looked the same everywhere. The underlying data varied, but the visual pattern did not.

Tier 3

Chart-type defaults

For genuinely new scenarios that did not fit Tier 1 or Tier 2, the guidance provided defaults for bar, line, horizontal, stacked, and segmented charts. This tier gave designers and PMs the flexibility to create new visualizations while still starting from a consistent baseline.

The Effect

New scorecards inherited consistency by default

The tiered system changed the working model for building new scorecards. Product Area SMEs and Analytics SMEs still defined the customer questions and data sources, but the visualization decisions were no longer open-ended. Most charts fell into Tier 1 or Tier 2, which meant the majority of visual decisions were already made before a designer was involved.

Tooltip taxonomy — single value, multi-value, and comparison

Layer 2
Quality of Life Improvements

Shifting tooltips from chart-type to data-type

Tooltips across the platform varied by chart type. A bar chart tooltip looked different from a line chart tooltip, even when both were displaying the same kind of data. The result was visual inconsistency that made the experience feel fragmented at the interaction level.

I mentored a junior designer to classify all existing tooltips and propose a new taxonomy based on data type rather than chart type. The classification produced three categories: single value, multi-value, and comparison. This meant tooltip behavior became predictable for users regardless of which chart they were interacting with.

Tooltip Taxonomy

Three categories based on what the user is reading, not which chart they are in

Category 01
Single value
The user is reading one data point. The tooltip displays the value, its label, and any relevant unit or date context.
Category 02
Multi-value
The user is reading multiple related data points at once, such as segments in a stacked chart. The tooltip groups all values with their labels in a consistent vertical layout.
Category 03
Comparison
The user is comparing two values. The tooltip displays both values with their labels and the difference between them, using a consistent format for delta display.

Empty States

Redesigning empty states at the system level

Empty states across scorecards had been treated as an afterthought, with inconsistent messaging and no clear guidance on what the user should do next. I redesigned empty states as a system-level pattern, establishing consistent messaging, visual treatment, and action paths that applied to every scorecard in the platform.

Layer 3
Information Architecture and System-Level Vision

A scalable scorecard framework

Scorecards give GTM teams visibility into whether product items are meeting the objectives they were created for. When the team was tasked with scaling beyond the original five scorecards, I proposed a systematic structure that layered on top of the existing system of components so that every new scorecard would follow a predictable pattern customers could rely on regardless of which item type they opened.

How It Started: The Original Five

Five scorecards, each with its own structure

When the effort began, five scorecards existed in the product. The two-SME collaboration model had shipped them, but each scorecard had been designed somewhat independently. Customers had to re-learn the structure every time they encountered a new one.

The question shifted from how to build more scorecards to whether a systematic structure could be layered on top of the existing components, bringing consistency to what had previously been bespoke.

What We Knew About User Behavior

Personas use scorecards in two distinct modes

Two things were clear about how personas actually use scorecards. Most of the time they want a quick health check. If everything looks fine, they leave. When something is off, they need a clear path to drill down into the details.

The framework had to serve both modes without forcing one to carry the weight of the other.

Mode 01
Quick health check
Persona opens the scorecard, scans the top-level data, and leaves if everything looks fine
Mode 02
Drill-down
When a signal looks off, the persona needs a fast, predictable path into the detail behind it
The Proposed Structure

A framework designed around how personas actually read scorecards

Every scorecard would open with an overview tab built for the high-level check-in. Subsequent tabs would be organized around the specific questions customers ask, following identifiable high-level categories that share a common structural pattern across item types.

Two principles tied the experience together
Principle 01
The overview tab maps directly to the subsequent tabs
Each section in the overview corresponds to a tab and surfaces the most important data from that tab. A persona can scan the overview, spot what needs attention, and know exactly where to go next.
Principle 02
Sections and tabs are ordered by walk-to-value
Both the overview sections and their corresponding tabs are ordered according to the walk-to-value for that scorecard, ensuring the most critical milestones in a customer's journey appear first.

How the Framework Reads

The overview becomes the map for the rest of the scorecard

A persona in check-in mode reads the overview top to bottom and sees the health of the customer journey in the order the customer walks it. A persona in drill-down mode sees the section that needs attention, reads the corresponding tab label, and moves straight into the detail.

Key Learnings

What this work taught me

Learning 01
Guidance at the right altitude prevents inconsistency that components alone cannot
Components provide building blocks, but they do not encode decisions about when and how to use them. The tiered data visualization guidance reduced variation across scorecards because it operated at the scenario level, not the component level. The framework reduced variation further because it operated at the information architecture level.
Learning 02
Mentoring is a design tool, not a management activity
The tooltip taxonomy emerged through structured mentorship of a junior designer. Classifying every tooltip in the platform required close reading of the existing experience that would have been difficult to do alone. The mentorship produced a better artifact than a solo exercise would have, and it built the junior designer's systems-level thinking at the same time.
